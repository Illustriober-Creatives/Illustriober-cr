## What Is Already Implemented

### Realtime ticket comments

- `apps/api/src/lib/realtime.ts`
  - Socket.IO is attached to the existing Node HTTP server.
  - JWT authentication occurs during the Socket.IO handshake.
  - Clients can join only tickets they own; admins can join any ticket.
  - Public and internal ticket rooms are separate.
  - `ticket:comment-created` is emitted to the correct room.
- `apps/api/src/index.ts`
  - Uses `createServer(app)` and initializes realtime before listening.
- `apps/api/src/routes/tickets.ts`
  - `GET /api/tickets/:id` returns comments.
  - Client responses exclude internal comments.
  - `POST /api/tickets/:id/comments` validates trimmed plain text, limits content to 4000 characters, persists, serializes, and emits comments.
  - Comment creation is rate limited before authentication.
- `packages/shared/src/index.ts`
  - Contains the shared comment schema and `TicketComment` type.
- `apps/web/src/lib/realtime.ts`
  - Shared browser Socket.IO client with access-token handshake auth.
- `apps/web/src/components/tickets/CommentThread.tsx`
  - Shared client/admin discussion UI, reconnect state, internal-note toggle, sender de-duplication, and responsive layout.
- `apps/web/src/app/dashboard/tickets/[id]/page.tsx`
  - Client ticket detail renders the public discussion thread.
- `apps/web/src/app/admin/tickets/[id]/page.tsx`
  - Admin ticket detail renders public and internal discussion and preserves comments when status is updated.

## Admin Dashboard Brief

Build the existing `/admin` route into an operational workspace, not a marketing page.

### First release scope

1. Authenticated admin-only access with a clear loading, forbidden, and session-expired state.
2. KPI strip for ticket counts by status: open, in review, in progress, and resolved.
3. Ticket queue with status, priority, client/project, assignee, updated time, and latest activity.
4. Filters and search that work on mobile as well as desktop.
5. Recent activity panel for new tickets, status changes, and new comments.
6. Unread/live comment indicators that update without a full page refresh.
7. Fast navigation from a queue row to the existing ticket detail page.
8. Useful empty, loading, error, and retry states for every data section.

### API questions to answer before implementation

- Does the current admin ticket list provide enough fields and pagination for the queue?
- Is an aggregate dashboard endpoint needed for status counts and activity, or can the first version derive these safely from existing responses?
- Do unread counts require a persisted read cursor, or is a session-only live indicator sufficient for the first release?
- Is ticket assignment already supported end-to-end, or should assignment be kept out of the first dashboard slice?

Prefer a small, explicit API addition over fetching every ticket into the browser. Keep authorization in the API, not only in the UI.

## Design and Interaction Constraints

- Reuse the current admin visual language and components. Preserve tokens such as `bg-surface`, `text-foreground`, `border-glass-border`, and `text-accent`.
- Keep the workspace dense and scannable: tables, compact panels, clear hierarchy, and predictable navigation.
- Do not introduce a second Socket.IO connection. Reuse `apps/web/src/lib/realtime.ts` and the existing ticket room protocol.
- Never expose internal comments through client-facing API responses or client rooms.
- Keep controls keyboard accessible and responsive with no horizontal overflow.
- Add icons to icon-capable actions and preserve existing button patterns.

## Production Notes

- Nginx for `api.illustriober.com` already forwards WebSocket upgrade headers to `localhost:4000`.
- The production PM2 list previously showed two `illustriober-api` processes. Process 0 owned the port and was stable; process 1 had a high restart count and appeared to be an `EADDRINUSE` duplicate. Do not scale or reload blindly. Inspect the PM2 ecosystem configuration and consolidate to one healthy process, or deliberately configure a multi-process Socket.IO adapter and session strategy first.
- The Vercel preview frontend may use the production API unless a preview API URL is configured. Realtime changes cannot be fully validated from preview until the API containing the Socket.IO server is deployed.
- The realtime work did not add a Prisma migration. Run `prisma generate` after dependency/build changes; do not invent a migration unless the schema changes.

## Required Workflow for Claude Code

1. Read `AGENTS.md`, this file, and the relevant route/component files.
2. Start from an up-to-date `main` branch and create a focused feature branch.
3. Use GitNexus before editing existing symbols:
   - `gitnexus_query` for dashboard/ticket concepts.
   - `gitnexus_context` for the route or component being changed.
   - `gitnexus_impact({ target, direction: "upstream" })` before modifying a function, class, or method.
4. Keep API, shared types, and UI changes separately understandable. Add focused tests for authorization, aggregation, filtering, and realtime behavior.
5. Before committing, run `gitnexus_detect_changes({ scope: "staged" })` and confirm only expected files/flows changed.
6. Verify with:

```bash
npm run build --workspace packages/shared
npm run build --workspace apps/api
npm test --workspace apps/api
npm run build --workspace apps/web
npm run lint --workspace apps/web
```

7. Push the new branch and open a PR against `main`. Keep the PR focused on the admin dashboard.
